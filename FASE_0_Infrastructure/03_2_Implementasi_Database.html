Menggunakan UUID (Universally Unique Identifier) untuk semua Primary Key.*Alasan:- Distributed System Ready: UUID dapat di-generate di client tanpa perlu round-trip ke DB- Security: Menyembunyikan jumlah total user/record (tidak sequential)- Merge-friendly: Jika ada multi-database sync, UUID tidak ada collision- PostgreSQL Native Support**: uuid-ossp extension sudah built-in*Trade-off:**- Storage overhead: 16 bytes vs 4/8 bytes untuk integer- Slower index scan dibanding integer, tapi acceptable untuk aplikasi skala universitas—### 1.7.2 TIMESTAMPTZ vs TIMESTAMP*Keputusan:** Menggunakan TIMESTAMPTZ (timezone-aware) untuk semua timestamp.*Alasan:- Timezone Handling: Otomatis convert ke UTC di storage, client bisa convert ke local timezone- Audit Trail Akurat: Waktu transaksi tidak ambiguous- Multi-Region Ready**: Jika ada disaster recovery di region lain, timestamp tetap konsisten—### 1.7.3 NUMERIC(4,3) untuk confidence_score*Keputusan:** Tipe NUMERIC dengan presisi 4 digit, 3 digit desimal (range: 0.000 - 0.999, dan 1.000).*Alasan:- Exact Precision: AI confidence selalu 0.0-1.0, NUMERIC tidak ada rounding error- Not Float/Double: Float punya precision loss, tidak cocok untuk financial/scoring logic- Range Validation**: CHECK constraint di database, bukan hanya di application layer—### 1.7.4 Enum-like VARCHAR dengan CHECK Constraints*Keputusan:** Menggunakan VARCHAR dengan CHECK constraint, bukan PostgreSQL native ENUM type.*Alasan:- Schema Flexibility: Enum di PostgreSQL hard to modify (ALTER TYPE requires recreating table)- ORM Compatibility: Beberapa ORM (Django) lebih mudah handle VARCHAR- Explicit Documentation: Check constraint explicit di schema- Zero-downtime Migration**: Kalau perlu tambah enum value, lebih mudah dengan VARCHAR—### 1.7.5 Cascade Delete vs Restrict*Keputusan:** Campuran - CASCADE untuk user, RESTRICT untuk rewards.*Alasan CASCADE:**- Saat user dihapus, hapus semua unggahan → hapus semua klasifikasi (data orphan tidak berguna)- Saat user dihapus, hapus semua point transactions → valid (audit trail individual)*Alasan RESTRICT:**- Rewards tidak boleh dihapus jika masih ada penukaran aktif (data integrity)- Mencegah accidental deletion- Admin harus handle penukaran terlebih dahulu—### 1.7.6 Nullable id_admin di education_materials*Keputusan:** id_admin nullable, ON DELETE SET NULL.*Alasan:**- Materi edukasi tetap valuable meski admin dihapus- Materi umum tidak selalu punya author specific (bisa system-generated)- Soft delete di admin side: simpan materi tapi mark dengan id_admin=NULL—### 1.7.7 Tidak Ada Soft Delete*Keputusan:** Hard delete dengan CASCADE, bukan soft delete (active column).*Alasan:**- Konsisten dengan dokumen RPL (tidak ada "is_deleted" column)- Data retention policy di application layer (audit log terpisah)- Simpler query logic (no WHERE is_deleted=FALSE di setiap query)- Kalau butuh audit trail, gunakan triggers + separate audit table (future enhancement)—## 1.8 Sample Datainclude (Materialized Queries)### View 1: v_leaderboard_user*Fungsi:** Peringkat pengguna berdasarkan total poin (descending).sql\nCREATE VIEW v_leaderboard_user AS\nSELECT \n ROW_NUMBER() OVER (ORDER BY Menggunakan UUID (Universally Unique Identifier) untuk semua Primary Key.*Alasan:- Distributed System Ready: UUID dapat di-generate di client tanpa perlu round-trip ke DB- Security: Menyembunyikan jumlah total user/record (tidak sequential)- Merge-friendly: Jika ada multi-database sync, UUID tidak ada collision- PostgreSQL Native Support**: uuid-ossp extension sudah built-in*Trade-off:**- Storage overhead: 16 bytes vs 4/8 bytes untuk integer- Slower index scan dibanding integer, tapi acceptable untuk aplikasi skala universitas—### 1.7.2 TIMESTAMPTZ vs TIMESTAMP*Keputusan:** Menggunakan TIMESTAMPTZ (timezone-aware) untuk semua timestamp.*Alasan:- Timezone Handling: Otomatis convert ke UTC di storage, client bisa convert ke local timezone- Audit Trail Akurat: Waktu transaksi tidak ambiguous- Multi-Region Ready**: Jika ada disaster recovery di region lain, timestamp tetap konsisten—### 1.7.3 NUMERIC(4,3) untuk confidence_score*Keputusan:** Tipe NUMERIC dengan presisi 4 digit, 3 digit desimal (range: 0.000 - 0.999, dan 1.000).*Alasan:- Exact Precision: AI confidence selalu 0.0-1.0, NUMERIC tidak ada rounding error- Not Float/Double: Float punya precision loss, tidak cocok untuk financial/scoring logic- Range Validation**: CHECK constraint di database, bukan hanya di application layer—### 1.7.4 Enum-like VARCHAR dengan CHECK Constraints*Keputusan:** Menggunakan VARCHAR dengan CHECK constraint, bukan PostgreSQL native ENUM type.*Alasan:- Schema Flexibility: Enum di PostgreSQL hard to modify (ALTER TYPE requires recreating table)- ORM Compatibility: Beberapa ORM (Django) lebih mudah handle VARCHAR- Explicit Documentation: Check constraint explicit di schema- Zero-downtime Migration**: Kalau perlu tambah enum value, lebih mudah dengan VARCHAR—### 1.7.5 Cascade Delete vs Restrict*Keputusan:** Campuran - CASCADE untuk user, RESTRICT untuk rewards.*Alasan CASCADE:**- Saat user dihapus, hapus semua unggahan → hapus semua klasifikasi (data orphan tidak berguna)- Saat user dihapus, hapus semua point transactions → valid (audit trail individual)*Alasan RESTRICT:**- Rewards tidak boleh dihapus jika masih ada penukaran aktif (data integrity)- Mencegah accidental deletion- Admin harus handle penukaran terlebih dahulu—### 1.7.6 Nullable id_admin di education_materials*Keputusan:** id_admin nullable, ON DELETE SET NULL.*Alasan:**- Materi edukasi tetap valuable meski admin dihapus- Materi umum tidak selalu punya author specific (bisa system-generated)- Soft delete di admin side: simpan materi tapi mark dengan id_admin=NULL—### 1.7.7 Tidak Ada Soft Delete*Keputusan:** Hard delete dengan CASCADE, bukan soft delete (active column).*Alasan:**- Konsisten dengan dokumen RPL (tidak ada "is_deleted" column)- Data retention policy di application layer (audit log terpisah)- Simpler query logic (no WHERE is_deleted=FALSE di setiap query)- Kalau butuh audit trail, gunakan triggers + separate audit table (future enhancement)—## 1.8 Sample Datainclude
